# 운동장 초기 표시 최적화

2026-10-24, 로컬에서 수정·검증. 커밋·푸시·배포 없음.

현재는 아래의 **실제 다운로드 최적화**까지 반영했다. 앞부분의 용량·대기 시간은 각 이전 단계 측정 기록이다.

## 원인과 변경

기존에는 운동장이 실제 화면에 들어온 후 `meadow-scene` 동적 모듈을 받고, Three.js 장면과 절차적 잔디를 구성한 다음 GLB 다운로드를 시작했다. 모바일에서는 잔디 섬유가 너무 작아 숨겨지지만 16,000개의 행렬·색상은 이미 계산하고 있었다.

- 화면에서 900px 이내에 접근하면 준비를 시작한다. 실제 가시성을 판단하는 관찰자는 별도로 두어 화면 밖 애니메이션·물리 계산 정지를 유지한다.
- 3D 모듈과 GLB를 동시에 요청한다. 모델은 낮은 요청 우선순위를 사용하며 준비 단계와 GLTF 파서가 같은 ArrayBuffer Promise를 공유한다. 실패한 요청은 캐시에서 지워 다음 시도에서 재요청할 수 있다.
- 잔디 섬유의 인스턴스 버퍼·행렬·색상은 카메라 배율상 보일 때만 만든다. 작은 화면은 기존 잔디 표면·범프·장난감 반응을 유지한다. 창이 넓어져 섬유가 필요하면 한 번 생성하고 재사용한다.
- GLB 원본(1,143,420B), 소품 배치, 카메라, 조명, 픽셀 비율과 그림자 품질은 변경하지 않았다. 새로운 이미지·모델·의존성 없음.

## 측정 범위

Chrome 로컬 프로덕션, 390×844px, CPU 4배 제한, 지연 100ms, 다운로드 200,000B/s, 캐시 비활성, 동작 감소 설정에서 각각 3회 측정했다. 메인의 네트워크 유휴 상태를 기다린 후 운동장으로 스크롤했다.

| 관찰 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 운동장 도착 후 가구 준비 표시 | 4,836 / 4,296 / 4,335ms | 3회 모두 도착 전에 준비됨 |
| 도착 후 첫 상태 갱신 처리 | 위 대기에 포함 | 334 / 234 / 213ms |
| 모델 응답 본문 전송량 | 480,664B | 동일 |

이 측정은 **준비가 끝난 뒤 도착했을 때의 체감 대기**다. 전체 페이지 다운로드가 이 비율로 빨라졌다는 의미는 아니다. 사전 요청이 다른 초기 요청과 겹쳐 모델 요청 자체의 소요 시간은 약 2.5초에서 약 8.1초로 늘었다. 용량 절감이 아니라 요청 순서와 시점의 개선이며, 곧바로 맨 아래로 이동하거나 네트워크가 더 느리면 준비를 기다릴 수 있다. 실기기 iOS/GPU별 측정은 하지 않았다.

로그: `tmp/yard-perf-before.log`, `tmp/yard-perf-after.log`. 동일한 모바일 구도의 전후 캡처에서 기존 잔디·가구 외형을 확인했다.

## 나비 연속 비행 반영 후 모바일 재측정

2026-10-24, 나비 애니메이션을 켜고 Chrome에서 390×844px로 다시 측정했다. 캐시 비활성, CPU 4배 제한, 지연 100ms, 다운로드 200,000B/s 조건이다. 가구 준비·애니메이션 실행 상태와 이후 두 번의 animation frame을 기다려 시간을 기록했다. 실제 기기 GPU 표시 지연까지 측정한 값은 아니다.

| 진입 시점 | 운동장 이동부터 준비 확인까지 (3회) | 관찰 |
| --- | --- | --- |
| 페이지 네트워크 유휴 후 이동 | 288 / 288 / 276ms | 세 번 모두 이동 전에 가구 준비 완료 |
| DOMContentLoaded 직후 즉시 이동 | 10,542 / 10,569 / 10,495ms | 세 번 모두 다운로드를 기다림 |

초기 문서부터 준비 확인까지는 약 11.4~11.9초였고, 모델 요청 자체는 약 8.2초였다. 따라서 미리 준비한 운동장에 도착했을 때의 개선은 확인되지만 **느린 연결에서 즉시 진입하는 초기 로딩 문제는 남아 있다**. 동일 조건의 변경 전 즉시 진입 기록은 없으므로 이 시나리오의 전후 개선율은 주장하지 않는다. 모델 요청은 매번 한 번, 응답 본문은 480,664B였고 JS 오류·가로 넘침은 없었다.

네트워크·CPU 제한이 없는 로컬에서 캐시를 끄고 즉시 이동한 추가 1회씩은 390px 269ms, 320px 303ms였다. 두 화면의 가구·나비 표시와 가로 넘침 없음을 캡처로 확인했다. 이 값은 실제 모바일 네트워크/기기 성능을 나타내지 않는다. 실기기 iOS/Safari는 미검증이다. 로그와 캡처: `tmp/yard-mobile-check.*`, `tmp/yard-mobile-local.*`, `tmp/yard-mobile-*.png`.

## 검증

- 모델 요청 공유·실패 후 재시도, 준비와 실제 가시성 분리, 초기 모바일 잔디 미생성·넓은 화면 생성·재사용을 테스트한다.
- PC1440/모바일390·320px에서 가구 로드, 네 장난감 키보드 던지기, 초기화, 화면 밖 정지, 동작 감소, ‘함께 갈 곳’ 키보드 이동 확인. 화면당 모델 요청 1개, 가로 넘침·JavaScript 오류 없음.
- lint·typecheck·387페이지 프로덕션 빌드 통과. 기본 병렬 테스트에서 기존 준비 가이드/배포 스크립트 테스트가 5초 시간 초과했으며, 제한 시간이나 판정 기준을 바꾸지 않고 `pnpm test --maxWorkers=2`로 67파일·1,720테스트 전체 통과를 확인했다. 실행 로그와 캡처는 `tmp/yard-opt-*`에 있다.

## 실제 다운로드 최적화 — 2026-10-24

사용자는 화질을 유지하면서 모바일에서 곧바로 하단에 내려가도 더 빨리 표시하도록 요청했다. 원본 Blender 내보내기를 `design/yard-blender/yard-furniture.source.glb`에 보존하고, `pnpm assets:yard`로 공개 GLB를 무손실 압축한다. KHR_meshopt_compression과 Three.js에 포함된 decoder를 사용한다. 정점 양자화·면 축소·삼각형 재정렬·텍스처 축소는 하지 않는다. 캐시 키는 `lossless-12`로 변경했다. 모델 요청에 지정하던 낮은 우선순위도 제거했다.

느린 네트워크에서 운동장과 경쟁하던 카드의 숨겨진 뒷면·다음 카드·포일 이미지 준비는 카드가 실제로 보일 때 시작한다. 고정 헤더에 가려진 영역을 제외하고 카드의 15% 이상이 보이면 한 번 초기화한다. 처음 보이는 앞면 그림은 그대로 먼저 요청한다. 카드를 다시 보러 올라오면 기존 이미지와 효과를 원래 품질로 준비하고, 이후 이동·뒤집기 동작을 유지한다. 이미 시작한 이미지 요청을 취소하는 구현은 아니다.

### 전송량과 동일성

| 항목 | 이전 | 현재 |
| --- | --- | --- |
| 공개 GLB 파일 | 1,143,420B | 633,616B (44.6% 감소) |
| HTTP gzip 응답 본문 | 480,664B | 357,581B (25.6% 감소) |
| 운동장 JS 청크의 gzip 본문 | 191,084B | 198,709B (decoder 포함 약 7.6KB 증가) |

- 압축 스크립트에서 59개 버퍼를 디코딩해 바이트 단위로 원본과 일치함을 확인한다. 실제 GLTFLoader 비교 테스트에서 16개 메시의 인덱스·모든 정점 속성·재질·위치/회전/크기도 동일하다.
- 원본 모델과 이전 빌드, 압축 모델과 새 빌드의 정지 장면을 같은 브라우저에서 비교했다. 1440×651, 390×372, 320×341 캔버스 각각에서 **RGB 픽셀 차이 0**. 이는 해당 고정 구도의 비교이며 모든 GPU/모든 프레임 비교를 뜻하지 않는다.
- 런타임 카메라·픽셀 비율·잔디·재질·그림자·조명·나비·물리는 변경하지 않았다. meshoptimizer 1.1.1은 개발용 encoder로 명시하고, Three.js에 포함된 decoder의 MIT 고지를 소프트웨어 고지 생성에 추가했다. 자산 감사 목록은 압축 파일의 새 해시와 기록으로 갱신했다.

### 모바일 즉시 진입 재측정

Chrome 로컬 프로덕션, 390×844px, CPU 4배 제한, 지연 100ms, 다운로드 200,000B/s, 캐시 비활성, 나비 애니메이션 활성. `DOMContentLoaded` 직후 운동장으로 이동하고 가구 준비/실행 상태 및 두 번의 animation frame을 기다렸다. 이전 재측정과 같은 조건으로 각 3회다.
