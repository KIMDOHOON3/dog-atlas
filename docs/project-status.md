# Dog Atlas 프로젝트 현재 상태

> 마지막 갱신: 2026-08-10
> 역할: 제품·디자인·코드·콘텐츠·검증 상태를 빠르게 파악하기 위한 살아 있는 문서
> 갱신 책임: 중요한 변경을 수행한 사람 또는 AI가 같은 변경 안에서 이 문서를 함께 수정한다.

## 1. 한눈에 보기

Dog Atlas(살아 있는 견종도감)는 강아지를 고려하는 사람이 외모와 인지도만으로 선택하지 않도록 돕는 한국어 편집형 웹 도감이다. 사용자는 견종을 발견하고, 역사와 원래 역할이 행동 경향과 현대의 돌봄 요구에 어떻게 이어질 수 있는지 읽고, 관심 후보를 저장해 같은 기준으로 비교한다.

현재는 초기 5종 또는 100종 MVP 계획을 넘어 **368종의 상세 콘텐츠와 시각 자산을 제공하는 로컬 데이터 기반 구현**까지 확장된 상태다. 마스터 카탈로그의 368종 모두 상세 페이지가 있다. 몽골 방카르는 첫 `verified-landrace` 편집 사례로 발행됐으며, 전용 포함 유형 스키마가 생기기 전까지 등록 상태는 `non-fci`로 유지한다.

## 2. 변하지 않는 제품 원칙

- 호기심과 따뜻함으로 사용자를 초대하고 책임 있는 판단을 돕는다.
- 견종 특성은 일반적 경향이며 개별 개체에 대한 보장이 아님을 밝힌다.
- 하나의 견종을 사용자의 정답으로 선언하지 않는다.
- 비교는 승자나 적합도 점수가 아니라 생활에서 체감할 차이를 이해시키는 데 사용한다.
- 입양을 미루거나 후보를 다시 검토하는 것도 유효한 결과다.
- 편집 초안을 수의학 또는 행동 전문가 검수 사실처럼 제시하지 않는다.
- 모바일 우선, 접근성, 빠른 로딩을 장식적 복잡성보다 우선한다.

## 3. 현재 구현된 사용자 경험

### 홈 `/`

- 날짜에 따라 시작 견종이 달라지는 수동 ‘오늘의 강아지’ 캐러셀
- 368종의 한글명·영문명·등록 별칭 검색
- 전체 견종 카드 탐색
- 재패니즈 스피츠, 보더 콜리, 그레이하운드를 활용한 편집형 발견 섹션

### 견종 상세 `/breeds/[slug]`

- 정체성, 형성 지역, 원래 역할, 역사 이야기
- 행동 단서와 여섯 개 경향 축
- 오늘의 생활과 돌봄 현실, 하루 장면
- 관련 견종과 출처
- 관심 견종 저장·해제

### 비교 `/compare`

- 저장하거나 URL로 전달한 2~3종 후보 비교
- 동일 기준의 행동·생활 정보 비교
- 모바일용 기준별 읽기 구조와 데스크톱 비교 구조
- 후보가 부족할 때의 빈 상태

### 전역 관심 견종 보관함

- 브라우저 `localStorage`에 최대 3종 저장
- 홈·상세·비교 화면 사이 상태 공유
- 저장 개수와 비교 가능 여부 안내

## 4. 디자인 현재 방향

- 분위기: 자연사 도감, 종이 질감, 현대적 반려동물 서비스의 중간 지점
- 색상: 아이보리 캔버스, 흰 패널, 짙은 잉크색 텍스트, 세이지·모스 계열 강조색
- 이미지: 성견의 견종별 비율을 살린 전신 카드 삽화와 원래 역할·지역을 설명하는 역사 장면
- 표현: 귀엽지만 유아적이지 않고, 장식보다 견종 실루엣과 정보 위계를 우선
- 레이아웃: 일반 콘텐츠 최대 1200px, 비교 콘텐츠 최대 1440px, 모바일 좌우 여백 16px 기준
- 접근성: 키보드 조작, 명시적 포커스, 충분한 대비, 최소 터치 영역, `prefers-reduced-motion`, 이미지 없이도 남는 핵심 정보

상세 규칙은 [`design-visual-guide.md`](design-visual-guide.md), 현재 화면의 기반 설계는 [`redesign-v2.md`](redesign-v2.md), 보관함·비교는 [`shortlist-design-spec.md`](shortlist-design-spec.md)를 참고한다.

## 5. 코드와 아키텍처

- Next.js 16 App Router, React 19, strict TypeScript
- CSS Modules와 `src/app/globals.css`의 전역 CSS custom properties
- Zod 4로 로딩 시 검증하는 로컬 TypeScript 콘텐츠
- Vitest, Testing Library, jsdom 기반 테스트
- 데이터베이스, 인증, CMS, 외부 검색 엔진, 전역 상태 라이브러리 없음

주요 경계:

| 영역 | 현재 원본 |
|---|---|
| 라우트 | `src/app/` |
| 공통 UI | `src/components/` |
| 상세 견종 368종 | `src/content/breeds/data.ts`, `detail-batch-*.ts` |
| 마스터 카탈로그 368종 | `src/content/breeds/master-catalog.ts` |
| 데이터 스키마 | `src/content/breeds/schema.ts`, `master-schema.ts` |
| 출처 레지스트리 | `src/content/breeds/master-sources.ts` |
| 카드 삽화 | `public/illustrations/v2/` |
| 역사 삽화 | `public/illustrations/v3/` |

현재 홈은 상세 `breeds` 전체를 사용한다. 마스터와 상세를 분리하는 아키텍처는 구현되어 있지만, 화면 번들 경계와 목록 DTO 최적화는 추후 다시 점검할 수 있다.

## 6. 콘텐츠와 자산 현황

코드와 테스트가 보장하는 현재 수치:

| 항목 | 현재 값 | 근거 |
|---|---:|---|
| 상세 견종 | 368 | `src/content/breeds/data.test.ts` |
| 마스터 카탈로그 | 368 | `src/content/breeds/master-catalog.test.ts` |
| 상세 발행 상태 | 368 published | `getMasterCatalogStats()` 테스트 |

| FCI definitive | 344 | 같은 테스트의 `registryStatus` |

| non-FCI | 6 | 같은 테스트의 `registryStatus` |

모든 상세 항목의 현재 `contentStatus`는 `mvp-editorial-draft`다. 이는 스키마 검증과 편집·출처 작업이 존재한다는 뜻이지, 수의학 또는 행동 전문가 검수를 완료했다는 뜻이 아니다.

## 7. 현재 알려진 문서 차이와 주의점

- [`mvp-scope.md`](mvp-scope.md)는 100종까지의 확장 기록을 담고 있으나 구현은 368종까지 진행됐다.
- [`catalog-20-proposal.md`](catalog-20-proposal.md)와 초기 디자인 명세의 ‘20종’ 표현은 역사적 계획이다.
- 이미지 프롬프트 배치 A·B 문서는 초기 15종의 제작 기록이며 전체 자산 제작 이력을 대표하지 않는다.
- 제품명은 코드 메타데이터에서 ‘살아 있는 견종도감’, 저장소와 문서에서는 ‘Dog Atlas’를 함께 사용한다.
- 아메리칸 핏불 테리어와 아메리칸 불리는 FCI가 아니라 UKC 등록 기준을 명시해 상세를 제공한다.
- 몽골 방카르처럼 공식 국제 견종 목록 밖의 토착 랜드레이스는 지역 정체성, 지속된 역할, 기관 또는 학술 근거, 다른 견종과의 명칭 경계를 확인하는 별도 트랙으로 다룬다.
- 국제 등록견, 국가 보존 토착견, 검증된 랜드레이스를 구분하는 편집 정책은 [`catalog-inclusion-policy.md`](catalog-inclusion-policy.md)에 정리했다. 현재 마스터 스키마 반영과 방카르 상세 제작은 후속 작업이다.

## 8. 검증 명령과 기준

중요한 코드·콘텐츠·UI 변경 뒤 아래 순서로 확인한다.

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

UI 변경은 추가로 390px, 768px, 1440px, 1920px 폭에서 확인한다. 비교 화면은 최대 1440px까지 확장할 수 있으며, 필수 정보는 모션이나 이미지가 없어도 접근 가능해야 한다.

최근 검증 결과(2026-08-10):

- `npm run lint` 통과
- `npm run typecheck` 통과
- `npm test` 통과 — 22개 파일, 74개 테스트
- `npm run build` 통과 — 368개 견종 상세 경로를 포함해 375개 정적 페이지 생성

이 문서를 갱신할 때 실제로 실행한 검증만 결과로 기록한다.

## 9. 다음 작업을 시작할 때 확인할 것

현재 저장소에 단일 확정 백로그는 없다. 다음 작업자는 요청 범위를 확인한 뒤 아래 순서로 판단한다.

1. 이 문서와 [`docs/README.md`](README.md)를 읽는다.
2. 작업 분야의 세부 명세와 최신 코드·테스트를 함께 확인한다.
3. 문서 속 과거 제안을 현재 구현으로 오해하지 않는다.
4. 제품이나 UI를 바꿀 때 단정적 추천, 적합도 점수, 승자 표현이 생기지 않는지 검토한다.
5. 기존 작업 트리 변경을 보존한다.
6. 변경을 검증하고, 범위·구조·수치·상태가 달라졌다면 이 문서를 함께 갱신한다.

## 10. 상태 문서 갱신 형식

이 문서는 작업 일지를 무한히 쌓는 곳이 아니다. 항상 ‘지금 사실인 것’만 유지한다.

- 상단 `마지막 갱신` 날짜를 바꾼다.
- 구현된 사용자 경험이 달라지면 3절을 수정한다.
- 디자인 시스템이나 주요 화면 방향이 달라지면 4절을 수정한다.
- 의존성, 데이터 흐름, 파일 경계가 달라지면 5절을 수정한다.
- 견종·자산·검수 수치가 달라지면 6절을 코드와 테스트에 맞춰 수정한다.
- 새로 발견한 불일치나 위험은 7절에 추가하고, 해결되면 제거한다.
- 실제로 실행한 최신 검증 상태는 8절에 기록한다.
- 결정의 역사와 이유가 중요하면 [`decisions.md`](decisions.md)에 별도 항목을 추가한다.
